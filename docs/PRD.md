## Product overview

Prospex is a self-hosted, open-source outreach platform for selling to local businesses. It finds leads on Google Maps, scores them, writes AI drafts in the owner's own voice, holds every message in a human-approval Outbox, sends through WhatsApp (and email) at a human pace, turns replies and follow-ups into drafts, and tracks each lead through a CRM pipeline. Nothing is sent without the owner's approval, and an opt-out is absolute. It is a Turborepo/pnpm monorepo: `apps/api` (NestJS), `apps/web` (Next.js dashboard), `apps/marketing` (landing site), `packages/database` (Prisma schema), `packages/types`. See `README.md` for the full description and `docs/features.md` for the verified feature list.

## 1. Vietnamese language support (replaces Indonesian)

### 1.1 Feature description

Prospex is currently bilingual in two senses, both hard-wired to Indonesian:

1. **Dashboard language.** The web app is available in English and Indonesian (`apps/web/src/lib/i18n`, about 950 strings, toggle in the header and on the login and register pages, choice kept in the `prospex_lang` cookie).
2. **Outreach language.** Everything the AI writes (marketing brief, lead-fit reasons, first messages, follow-ups, replies, email subjects, bulk-template messages) and the fixed wording the system adds (opt-out line, email footer, unsubscribe page, canned replies) is produced in `"indonesian"` or `"english"`. The value is stored per campaign (`campaigns.language`) and per marketing brief (`marketing_briefs.language`), both defaulting to `"indonesian"`.

This feature **replaces Indonesian with Vietnamese** in both senses. After it ships, the supported languages are **English and Vietnamese only**, the header toggle reads **EN | VI**, and a Vietnamese-speaking business owner can use the whole dashboard in Vietnamese and have Prospex write, check and send outreach in natural Vietnamese.

Decisions already made (not to be reopened in this feature):

- Indonesian is removed as a selectable language in the UI and in AI output. It is not kept as a third option.
- Scope is the **web UI** and **AI-generated content** (including the fixed system wording that is part of a sent message).

Related sections: none yet (this is the first feature section). It touches the invariants in `CLAUDE.md` for Messaging (approval, opt-out), Email (footer, `List-Unsubscribe`), Marketing (grounded evidence, untrusted text) and the i18n rules for the Frontend; all of them stay unchanged (see NFR-8).

### 1.2 User story

As a **Vietnamese-speaking business owner** who uses the Prospex dashboard to find and contact local businesses, I want to **read the whole interface in Vietnamese and have every draft, reply, follow-up and email written in polite, natural Vietnamese with correct diacritics** so that **I can review and approve messages quickly, and the businesses I contact receive messages that read as written by a Vietnamese professional, not as a machine translation.**

Secondary: As an **English-speaking user**, I want the English interface and English drafts to behave exactly as they do today.

### 1.4 Functional requirements

#### A. Web UI: language model and dictionaries

- **FR-1** `Lang` becomes `"en" | "vi"`. `parseLang(value)` returns `"vi"` only for the exact value `"vi"` and `"en"` for everything else, including the legacy value `"id"`, an empty or missing cookie, and any unexpected string. The cookie name stays `prospex_lang`. `lang.ts` stays free of `"use client"` and of imports of the dictionaries (the root layout imports it on the server).
- **FR-2** The Indonesian dictionaries are removed and replaced one-to-one by Vietnamese ones: `id.ts` becomes `vi.ts` and each `features-<name>.id.ts` becomes `features-<name>.vi.ts` (admin, auth, billing, campaigns, knowledge, leads, marketing, pipeline, templates, workspace). No `*.id.ts` file and no export named `id`, `idAll` or `*Id` remains. The workspace dictionary export `workspaceId` (`features-workspace.id.ts`) is renamed `workspaceVi`, because the name `workspaceId` reads as a database id and is a rename trap for a search-and-replace of `Id` (verified: `features-workspace.id.ts` exports `workspaceId`, imported by `messages.ts`).
- **FR-3** `messages.ts` exports `viAll: Record<MessageKey, string>` built from the Vietnamese files, so that a missing or misspelled Vietnamese key is a TypeScript compile error exactly as it is for Indonesian today. `index.tsx` uses `dictionaries: Record<Lang, Record<MessageKey, string>> = { en: enAll, vi: viAll }`. English stays the source of truth: adding a key to an English file is the only way to create a key.
- **FR-4** Every Vietnamese string preserves the exact interpolation placeholders of its English source (`{n}`, `{date}`, `{days}`, `{time}`, `{industry}`, `{location}`, and all others), including the literal template tokens `{nama}` and `{kategori}` shown in `tpl.placeholders` (see Open question OQ-5). A test enumerates all keys and fails when the set of `{placeholder}` names differs between English and Vietnamese for any key. The runner is the browser-less Playwright spec `tests/e2e/i18n-dictionaries.spec.ts` (AC-3); `apps/web` has no test script today and no runner is added to it (NFR-1).
- **FR-5** Vietnamese UI text uses natural, concise product wording: Vietnamese diacritics always present, a consistent second-person form across the app (`bạn`), consistent terms for recurring concepts (campaign, lead, draft, outbox, approve, pipeline, knowledge base, brief), sentence case for buttons and labels, and no machine-translated word order. Product names (Prospex, WhatsApp, Outbox, Pipeline if kept as a proper noun) follow one glossary that is committed with the dictionaries (see 1.9).
- **FR-6** The `camp.lang.indonesian` key becomes `camp.lang.vietnamese`. The English dictionary labels it "Vietnamese" and the Vietnamese dictionary labels it "Tiếng Việt". The label for English in the Vietnamese dictionary is "Tiếng Anh".

#### B. Web UI: toggle, cookie, first paint

- **FR-7** `language-toggle.tsx` renders two options in this order: `EN` (title "English") and `VI` (title "Tiếng Việt"). The accessible group label stays `t("header.language")`, the active option keeps `aria-pressed`. The toggle appears in the same four places as today (header, login page, register page, auth heading).
- **FR-8** `setLang("vi")` writes `prospex_lang=vi; path=/; max-age=31536000; samesite=lax` and sets `document.documentElement.lang = "vi"`; `setLang("en")` does the same with `en`. Cookie attributes do not change from today. If cookies are blocked the choice lasts for the session only (existing behaviour kept). A click on the already-active option is a no-op only under the condition in FR-10.
- **FR-9** The root layout keeps reading the cookie on the server and renders `<html lang="en">` or `<html lang="vi">`, and passes the same value to `I18nProvider initial`, so the server HTML already carries the right language (no flash of the wrong language, no hydration mismatch).
- **FR-10** A returning user whose cookie holds the legacy value `id` (or any other invalid value) is shown English. The cookie is not rewritten automatically; no error, no redirect, no banner. Toggle click rule (resolves OG-1): clicking the already-active option is a **no-op (no cookie write, no state change) only when the raw `prospex_lang` cookie value, as read on the client, already equals the active value** (`en` while English is active, `vi` while Vietnamese is active). In every other case a click writes the cookie (FR-8). Therefore, with a cookie of `id`, an invalid value or no cookie, the page shows English, a click on `EN` **writes `en`** (the stale value is replaced on the first explicit choice, `EN` or `VI`), and a click on `VI` writes `vi`. The comparison uses the raw cookie value, not the parsed `lang`, because `parseLang` maps `id` to `en` (FR-1) and would hide the difference.
- **FR-11** Dates, times, relative times and numbers are formatted through **one** shared helper set. `lib/i18n/lang.ts` (server-safe, no `"use client"`) exports `localeOf(lang: Lang): "en-US" | "vi-VN"` (`Intl.RelativeTimeFormat` uses the same locale's language, `en` / `vi`); a client hook `useFormat()` returns `{ date, dateTime, number, relative }` bound to the active `lang`. The formatting logic is the pure function `makeFormat(lang: Lang)` in the same `lib/i18n/lang.ts` (no React, no `"use client"`), which returns that same `{ date, dateTime, number, relative }` object; `useFormat()` is a thin wrapper that calls `makeFormat` with the active `lang`, so the formatting can be tested without rendering a component (G-5 (plan), 1.8.6). All 12 components listed in 1.3 use it; no inline `lang === "id"` conditional and no hard-coded `"id-ID"` remains in `apps/web/src`. The two places that ignore `lang` today (`billing-page.tsx`, `pipeline-page.tsx`) follow the active language. Five lines with bare `.toLocaleString()` calls that ignore `lang` and use the browser locale (six calls) are routed through `useFormat().number` too (verified by Grep): `dashboard/overview.tsx:50`, `knowledge/knowledge-page.tsx:188`, `style/style-page.tsx:239`, `:257` and `:310` (two calls on that line). The currency prefix "Rp" is out of scope (OQ-6).
- **FR-12** The web app loads the Inter font with `subsets: ["latin", "vietnamese"]`, so stacked diacritics (for example "ệ", "ử", "ằ") render in Inter and not in a fallback font. No layout shift beyond the existing font swap.

#### C. Web UI: language sent to the API

- **FR-13** One shared, server-safe mapping in `lib/i18n/lang.ts` converts `Lang` to the API value: `toApiLanguage(lang: Lang): OutputLanguage` returns `"vietnamese"` for `"vi"` and `"english"` for `"en"`. Next to it, `effectiveOutputLanguage(value: unknown)` returns the language the system will actually use for a stored value (`"vietnamese"` only for the exact value, `"english"` otherwise; the web mirror of FR-19, used by FR-14 and FR-15). The web keeps its **own** two-value union (`"vietnamese" | "english"`); it does not import `@prospex/types` or any API module for it (see FR-16: the contract is enforced by the DTOs and AC-6/AC-7). `brief-page.tsx` (brief generation) and `template-panel.tsx` (template generate and template apply) use it. The literals `"indonesian"` and `lang === "id" ? "indonesian"` no longer appear in `apps/web/src`.
- **FR-14** The campaign form (`create-campaign-form.tsx`) offers `vietnamese` and `english`, defaults to `vietnamese`, and submits the selected value unchanged (no fallback to Indonesian). `campaign-config.tsx` lists `LANGS = ["vietnamese", "english"]` and only **displays** the campaign language (no web screen edits a campaign's language through `PATCH /campaigns/:id`, see FR-19 c). `marketing/types.ts` types the field `"vietnamese" | "english"`. When the campaign form is auto-filled from a saved brief, the form takes the brief's **effective** language, `effectiveOutputLanguage(b.language)` (FR-13), where `b.language` is the brief's **column** value, so a legacy `"indonesian"` brief fills the form with `english`, matching what the brief page shows (G-4). Today the autofill reads `b.campaign.language` inside the brief JSON; the code is changed to read the column, and because new briefs store the same value in the column and in `content.campaign.language` (G-7, requested language wins), the two places agree for every new brief (1.8.6).
- **FR-15** When the web app shows a campaign or brief whose stored language is the legacy `"indonesian"` (or any value other than the two supported ones), it shows the language the system will actually use (see FR-19, computed with `effectiveOutputLanguage`, FR-13), not the raw stored text and not a blank.

#### D. API: language values, validation, defaults

- **FR-16** The supported API values become `"vietnamese"` and `"english"`. One module, `apps/api/src/common/language.ts` (not under `ai/`: the language is used by `marketing/`, `messaging/`, `email/`, `campaigns/` and `scraper/` as well), exports:
  1. `OUTPUT_LANGUAGES = ["vietnamese", "english"] as const` and `type OutputLanguage = (typeof OUTPUT_LANGUAGES)[number]`;
  2. `toOutputLanguage(value: unknown): OutputLanguage`, returning `"vietnamese"` only for the exact value `"vietnamese"` and `"english"` for everything else (FR-19);
  3. the DTO decorator `IsOutputLanguage()`, which composes `ValidateIf((o, v) => v !== undefined)` + `IsIn(OUTPUT_LANGUAGES)` + `ApiProperty` (FR-17);
  4. `LANGUAGE_LABEL: Record<OutputLanguage, string>` (shipped values: `"Vietnamese (tiếng Việt)"` and `"English"`; tests import the constant instead of a literal), the only way a language name enters a prompt, so that a stored value is **never interpolated into a prompt** (prompt-injection and legacy-value safety).

  Every place that today repeats `=== "english" ? "english" : "indonesian"` calls the normaliser instead. The API does **not** import `@prospex/types` at runtime for this: that package's entry point is the raw `src/index.ts` and the API runs `node dist/main`. The web keeps its own two-value union (FR-13); the contract between the two is enforced by the DTOs and AC-6 / AC-7. Shared text helpers live in `apps/api/src/common/text.ts` (FR-44). The string literal `"indonesian"` appears in `apps/api/src` only in the legacy-compatibility code and its tests (FR-19, FR-27, FR-29, FR-33; the full list is G-22).
- **FR-17** Request validation: every request field named `language` is validated with the shared `IsOutputLanguage()` decorator (FR-16): `ValidateIf(v !== undefined)` + `@IsIn(["vietnamese", "english"])` + `ApiProperty`. The field is optional (omitted passes), but an explicit `null` is **not** skipped and returns 400 (a plain `@IsOptional()` would skip `@IsIn` for `null` and let it reach Prisma as a 500). This adds the validator to `POST /campaigns` and `PATCH /campaigns/:id` (today `@IsString()`; see FR-48 for the `PATCH` DTO), and changes the allowed set on `POST /marketing/brief/generate`, `POST /messaging/templates/generate` and `POST /messaging/templates/apply`; `POST /style/draft` gains it through FR-43. A request with `"indonesian"` or any other value returns HTTP 400 through the existing `HttpExceptionFilter` (for JWT-authenticated clients; `ApiKeyGuard` is not applied to any controller, so these routes are tested with JWT only and a request with an `ApiKey` header gets 401 as on `main`, 1.8.6). (This tightens the contract of the two campaign routes; see OQ-4.)
- **FR-18** Defaults when `language` is omitted: campaign create stores `"vietnamese"`; brief generate uses `"vietnamese"`; template generate and apply use `"vietnamese"`; `POST /style/draft` uses `"vietnamese"` (FR-43); a manual email draft stores `context.language = "vietnamese"` (see OQ-7). The `CreateCampaignDto` Swagger default becomes `"vietnamese"`.
- **FR-19** Legacy values: the normaliser returns `"vietnamese"` only for exactly `"vietnamese"` and `"english"` for **every other input**, including the stored legacy value `"indonesian"`, `null`, `undefined` and unknown strings. Consequences that must hold: (a) existing campaigns, briefs and queued email drafts keep working without a migration of row data; (b) nothing is ever written in a language the owner did not choose, and nothing is ever written in Indonesian; (c) the owner can switch the campaign to Vietnamese at any time through `PATCH /campaigns/:id` or by regenerating the brief; **no web screen edits a campaign's language through `PATCH`** (`campaign-config.tsx` only displays it, FR-14), so (c) is reachable only through the API or by regenerating the brief (F-3, 1.8.6). The rationale and rejected options are in 1.7.
- **FR-20** Every consumer of the campaign or brief language uses the normaliser at the point of use (not only at write time), so rows created before the change are handled identically. This covers at least: `message-writer.service.ts` (outreach, follow-up, reply, subject), `template.service.ts`, `email.service.ts` (including reading `context.language` of queued drafts), `email-sender.service.ts`, `scraper.controller.ts` and `scraper.processor.ts` (lead-fit assessment), `inbound.service.ts`, `followup.service.ts`, `messaging.service.ts`, `brief.service.ts`, `style.service.ts` (FR-43), and `coerceBrief` in `brief-schema.ts` (which today also reads `campaign.language` from model output; the **requested** language wins over the model's value, G-7).

#### E. AI-generated content: prompts and writing quality

- **FR-21** Every prompt builder that branches on language gains a Vietnamese branch and loses its Indonesian branch: `brief-prompt.ts`, `marketing-ai.service.ts`, `fit.service.ts` (language label "Vietnamese"), `chat-import/style-prompt.ts` (`describeStyle`, `buildOutreachMessages`, `SERVICE_STYLE`, the owner-style header), `subjectFor`, and the reply path. The reply prompt (`buildDraftMessages`) and the reply judge (`judgeMessages`) receive the language as an explicit parameter (they have none today) and write replies in the campaign's language. `buildDraftMessages` has **one definition**, in `ai/chat-import/style-prompt.ts`, and gains a **required** `language: OutputLanguage` parameter; its three callers are `messaging/message-writer.service.ts`, `ai/style.service.ts` and `apps/api/scripts/eval-style.ts` (1.8.6). - **FR-22** Vietnamese output requirements, enforced in the prompt **and** checked in code where code can check them:
  1. Vietnamese diacritics and tone marks are always present. Output without diacritics ("Chao anh/chi") is a defect and is rejected and regenerated through the existing retry loop.   2. Text is Unicode NFC. The normaliser (FR-24) converts NFD input to NFC and never removes, replaces or reorders a diacritic.
  3. Register is polite and professional by default. - **FR-39** (G-9) `isCustomerBusinessTerm` and `NOT_A_CUSTOMER_BUSINESS` (marketing customer-search-term filter) get Vietnamese job-title and seller-service words (for example `giám đốc`, `phần mềm`, `dịch vụ`) so they are not accepted as customer search terms (customer search terms are business types, not job titles or the seller's own services, `CLAUDE.md`). - **FR-40** Offer-kind detection. `detectOfferKind` (`ai/chat-import/offer-kind.ts`) recognises Vietnamese **service** cues (for example `dịch vụ`, `theo yêu cầu`, `thiết kế`, `phát triển`, `gia công`, `tư vấn`) and Vietnamese **product** cues (for example `gói tháng`, `dùng thử`, `phần mềm có sẵn`), with the Unicode-aware boundaries of FR-44. Why it matters (today's defect): a Vietnamese service brief is detected as `product`, so service drafts receive a demo or free-trial pitch and the `outreachProblems` service checks (self-introduction, product-pitch words, FR-26) are skipped.
- **FR-41** Brief use and vertical checks (`marketing/brief-use.ts`). Tokenisation of Vietnamese is by **syllable bigrams on NFC text**; the minimum word length of 4 does not apply to Vietnamese (today `tokens()` drops words shorter than 4 characters, and most Vietnamese syllables have 2 to 4 letters, so a Vietnamese brief would yield almost no tokens). `offerListWords` and `GENERIC_WORDS` gain Vietnamese list markers (`như`, `ví dụ`, `bao gồm`), separators (`và`, `hoặc`, `đến`) and generic words (`cửa hàng`, `dịch vụ`, `công ty`, `cho thuê`). `foreignVerticalWords` flags a Vietnamese draft that names another segment's business. The English tokenisation is unchanged (NFR-7).
- **FR-42** Language-aware or language-neutral reply machinery. (a) `messaging/reply-intent.ts` `CLEAR_INTENT` (used by `looksAutomaticByTiming`) gains Vietnamese clear-intent cues; a Vietnamese reply with clear intent (`giá bao nhiêu`, `được`, `gửi giúp em`) arriving within **45 seconds** is **not** classified `auto_reply`. (b) The `intentMessages` LLM prompt, whose speaker labels are Indonesian (`Saya` / `Mereka`), uses the protocol markers of FR-32. (c) `judgeMessages` / `parseJudge` in `reply-plan.ts` take the language parameter (FR-21) and the `NO:` marker (FR-32). (d) The `alreadyIntroduced` regex in `message-writer.service.ts` (`saya|kami dari`) becomes language-aware (Vietnamese: for example `em là`, `tôi là`, `chúng tôi`, `bên em`, `đến từ`) or language-neutral. (e) The default texts `bisnis milik pengguna` (in `message-writer.service.ts` and `ai/style.service.ts`) are language-aware (a Vietnamese default text for `vietnamese`, English wording for `english`; the Vietnamese wording is reviewed by the native speaker, NFR-9), taken from the per-language tables (FR-49).
- **FR-43** `POST /style/draft` (`ai/style.controller.ts`, `DraftDto`; `ai/style.service.ts`, which calls `buildDraftMessages` from `ai/chat-import/style-prompt.ts`, FR-21) accepts an optional `language`, validated with `IsOutputLanguage()` exactly as in FR-17 (omitted gives `"vietnamese"`, `null` or any other value returns 400). `ai/style.service.ts` passes the resolved language to `buildDraftMessages` (required parameter, FR-21), which writes the draft in that language. In the web, `style-page.tsx` sends `toApiLanguage(lang)` (FR-13). The endpoint is added to the 1.9 table. (Today the route takes no language and its prompt is Indonesian only.)
- **FR-44** Unicode normalisation. Vietnamese text can arrive precomposed (NFC) or decomposed (NFD, from some phones, exports and models); every length check, pattern and equality test must see one form.
  1. **At ingest, to NFC:** inbound WhatsApp messages (`messaging/wa-text.ts` and `InboundService`); the output of the chat-export parser; knowledge and brief source text **before** chunking and embedding (so the same text does not embed differently); owner edits in `MessagingService`, **body and subject**, at **save and at approve time**, so that what the owner approved is byte-identical to what is sent (an email subject edited in NFD is stored and sent as the same NFC bytes).
  2. **Immediately after every model call:** `generate()`, `subjectFor`, `coerceBrief`'s `str()`, and fit reasons.
  3. **Defensively inside every matcher, before any length check:** `isOptOut`, `looksLikeInjection`, `classifyReply`, `checkReply`, `outreachProblems`, `draftRisks`, `stripOptOutHints`.
  4. **Word boundaries** in every new pattern are `(?<![\p{L}\p{M}\p{N}])…(?![\p{L}\p{M}\p{N}])` with the `u` flag. In NFD a tone mark is a combining mark (`\p{M}`), so a boundary class of `\p{L}\p{N}` alone would split a word in front of its own mark (this corrects the text of G-9 in 1.8.2). ASCII `\b` is never used for Vietnamese.
  5. **Tokenisers** that replace `[^\p{L}\p{N}\s]` with a space (`ai/chat-import/style-stats.ts:32` and `marketing/brief-use.ts:14`) normalise to NFC first; otherwise decomposed marks are replaced by spaces and split every accented word.
  6. `opt-out.ts` length limits (300 characters, `SHORT_MAX` 80) are measured **after** NFC.
  7. Shared helpers live in `apps/api/src/common/text.ts`: `nfc(s)`, `fold(s)` (NFD, strip `\p{M}`, `đ` to `d`, lower-case; for boolean tests only, **never** to rewrite a draft or stored text), `hasVietnameseMarks(s)` (true when the text contains `đ` or `Đ`, a letter carrying a Vietnamese vowel modification `ă â ê ô ơ ư` (either case), or, after NFD, one of the five Vietnamese tone marks U+0300, U+0301, U+0303, U+0309, U+0323; the stroke letter `đ` / `Đ` **counts as a mark** although it is not a combining mark, resolves OG-2; works on NFC and NFD input), a builder for the Unicode word-boundary regex of item 4, and `sliceChars(s, n)` (slice by code point). No other module re-implements these.
  8. **`clip()` and `headerLine()`** (the existing helpers that bound outside text and email header text) normalise to NFC and cut by code point (`sliceChars`), not by UTF-16 unit, so a clipped value never ends in an orphaned tone mark and a clipped NFD input has the same result as the NFC one.
- **FR-45** (amends G-18 and AC-11; **security amendment as shipped**) Opt-out folding rule. Shipped behaviour in one paragraph: a message with **any Vietnamese mark** is matched only against the **diacritic phrases** (on the NFC original); a message with **no mark** is matched against the **folded phrases** and the bare tokens `dung` / `ngung`. Known false negatives, accepted and recorded in 1.14: mixed text such as `dung gui nua ạ` (a mark plus unmarked words) and a bare `đừng` are **not** detected as opt-outs. The text below is the original rule, kept for the reasoning and the test cases. The **bare-token** rule (the folded form `dung` as the **whole message**) applies **only when the message contains no Vietnamese mark at all** (`hasVietnameseMarks` is false; `đ` and `Đ` count as marks, FR-44.7, so a bare `đung` / `Đung` is **not** an opt-out; resolves OG-2). **Folded phrase patterns** that carry more than one word (`dung gui`, `dung nhan`, `dung lien he`, `dung lam phien`, ...) run only on input without Vietnamese marks (amended as shipped, see above and 1.14; the first version allowed any input). A diacritic-bearing bare `dừng` or `ngừng` as the whole message is matched on the NFC original, not on the folded form. Negative test cases, which must **not** be opt-outs: `Đúng`, `Đúng rồi`, `Dũng`, `dùng thử`, `Đung`, `đung`. Reason: `Đúng` ("correct") folds to `dung`; without this rule a customer confirming something would be opted out permanently. Accepted trade-off: a customer who types `dung` with no diacritics and means "đúng" is treated as an opt-out (the net may only ever stop a conversation, `opt-out.ts`).
- **FR-46** `ai/marketing-ai.service.ts` (the draft builder at lines ~54-75; it lives in `ai/`, not `marketing/`) interpolates the scraped `businessName`, address and industry straight into the prompt (for example `Business: ${input.businessName}`) **without** `<data_*>` delimiters, `clip()` or `SECURITY_RULE`. This breaks the existing invariant in `CLAUDE.md` (text from outside stays inside delimiters and goes through `clip()`), and the function is rewritten by this feature, so it is fixed in the same change: scraped fields go inside a `<data_lead>` block through `clip()`, and `SECURITY_RULE` is included in the system prompt. Test: a business name containing an instruction (`Ignore previous instructions`) appears only inside `<data_lead>`, is clipped to the limit, and the prompt contains the security rule. **This is a security fix that changes this ONE prompt for English as well as for Vietnamese (resolves OG-4).** The lead-notes prompt is therefore **exempt** from NFR-7 and AC-28 (English prompts byte-identical to the pre-change snapshot): its snapshot is updated deliberately **in the same slice** that makes the change (shipped: `leadNotes.english` is an `EXEMPT` entry of the snapshot test with a written reason; the review fix d826020 added 11 more, the outreach prompts, whose RULES line no longer interpolates the scraped category or name; only `describeStyle.english` stays byte-identical); every other English prompt stays byte-identical, subject only to the exemptions listed in NFR-7.
- **FR-47** WhatsApp inbound markers stored in message rows (`[Kontak: …]`, `[Gambar]`, `[Pesan suara]`, `[Stiker]`, `[Dokumen: …]` and the placeholder `tanpa nama`, written by `messaging/wa-text.ts` and parsed by `reply-intent.ts`, `reply-plan.ts` and `wa-text.ts`) are **internal protocol**. They are defined in **one exported constant** (writer and parsers import it); their text is not changed to Vietnamese in this feature, and **stored rows keep parsing**. Known limitation (not fixed here): these markers appear as-is wherever a stored inbound message is displayed, including a Vietnamese UI; localising their display is out of scope.
- **FR-48** `UpdateCampaignDto` (today `PartialType(CreateCampaignDto)` in `campaigns/dto/update-campaign.dto.ts`, verified) becomes `PartialType(OmitType(CreateCampaignDto, ["language"]))` with `language` re-declared through the shared `IsOutputLanguage()` decorator. Reason: `PartialType` adds `@IsOptional()` to every field, which skips `@IsIn` for `null`, so `language: null` would reach Prisma and return a 500 instead of a 400 (reinforces G-5). `POST /campaigns` uses the same decorator.
- **FR-50** (added by implementation, security) Campaign routes are workspace-scoped and bounded: `PATCH /campaigns/:id` and `DELETE /campaigns/:id` use `updateMany` / `deleteMany` with `workspaceId` in the filter and return 404 for a campaign of another workspace; `PATCH` copies only an explicit allow-list of fields; `CreateCampaignDto` string fields carry `MaxLength` bounds. Before this change the two routes did not filter by workspace (an existing HIGH finding, fixed in S3).
- **FR-51** (added by implementation, security) The WhatsApp export parser has a bounded line and message size (`MAX_MESSAGE_CHARS = 10_000`) and no backtracking-prone pattern (the old parser needed 12.9 s on a 120,000-line input and now needs about 0.1 s); and the first line of each message is no longer cut at about 400 characters (a bug that silently truncated owner text and skewed AI Style statistics).
- **FR-49** Per-language data is held in **typed `Record<OutputLanguage, …>` tables co-located with the concern that uses it**, not in a central language-pack object: `OPT_OUT_HINT` (`opt-out.ts`), `REPLY_TEMPLATES`, `FALLBACKS` and `CHECK_RULES` (`reply-plan.ts`), `OUTREACH_RULES` (`outreach-check.ts`), `RISK_RULES` (`draft-risk.ts`), `FOOTER_LINE` (`email/email-utils.ts`), `CLOSINGS` and `LINK_LABEL` (`message-writer.service.ts`), the default business text and the self-introduction pattern of FR-42 d and e (`message-writer.service.ts`, `ai/style.service.ts`), `ORTHO_RULES` (`ai/orthography.ts`), plus the `OUTPUT_RULES` prompt blocks (FR-21). Because every table is `Record<OutputLanguage, …>`, adding a third language to `OUTPUT_LANGUAGES` is a **compile error** in each file until it is filled in (NFR-11). Tables are keyed by the **output** language only; inbound pattern sets are not (FR-31).

### 1.5 Non-functional requirements

- **NFR-1 Compile-time completeness.** Every UI key exists in both dictionaries by construction: `viAll: Record<MessageKey, string>`. Deleting any key from any `*.vi.ts` file makes `pnpm --filter @prospex/web exec tsc --noEmit` fail. No `any`, no runtime-only key checking, no new i18n dependency, and no new test dependency: `apps/web` has no test script today, and adding `tsx` or `node --test` to it is **not** done without the user's approval (the parity checks run in Playwright, AC-3).
- **NFR-2 No flash of the wrong language.** The language is decided on the server from the cookie and rendered into the first HTML (`<html lang>` and text). A hard reload with `prospex_lang=vi` never shows English text first.
- **NFR-3 Cookie behaviour.** Name `prospex_lang`; values `en` and `vi` are written; `id`, absent or unknown values read as English (FR-1, FR-10); attributes unchanged (`path=/`, one year, `samesite=lax`); no server-side session or database field stores the UI language; no personal data in the cookie.
- **NFR-4 Performance.** The client bundle carries two dictionaries today and still carries two; the gzip size of the i18n chunk may grow by at most 10 percent compared with the Indonesian build (Vietnamese diacritics are multi-byte). `t()` stays O(1). Language switching re-renders without a network request. The orthography functions and the opt-out and intent classifiers are linear in input length with no backtracking-prone patterns; `isOptOut` and the intent rules run only on text already capped by the existing limits and must handle a 300-character hostile input within `HOSTILE_MS_SMALL`; `looksLikeInjection` scans the whole text in windows of 2,000 characters with 200 characters of overlap (total cost linear, nothing skipped) and uses bounded gaps (`[^\n]{0,60}`) in new patterns, and must handle a 2,000-character hostile input within `HOSTILE_MS_SMALL` and a 20,000-character one within `HOSTILE_MS_LARGE` (FR-30). **Hostile-input limits live in one module, `apps/api/src/common/hostile-limits.ts`** (1.8.6): `HOSTILE_MS_SMALL = 500` (inputs of at most 2,000 characters), `HOSTILE_MS_LARGE = 1500` (inputs of at least 20,000 characters), and `assertLinear`, which times the matcher on a 2,000-character and a 20,000-character input, takes the best of 3 runs for each, and fails unless `t(20k) <= 30 * max(t(2k), 5)` (times in milliseconds). Every hostile-input test imports these; no test hard-codes its own limit. Normalisation (`nfc`, `fold`) is a single linear pass per message. Prompt size for Vietnamese must not exceed the English prompt size by more than 25 percent (Vietnamese tokenises less efficiently), so that small local models keep working.
- **NFR-5 Security and privacy.** No new endpoint, no new secret, no new dependency. Text from outside stays delimited (FR-23). Unicode handling must not enable bypasses: opt-out and injection matching normalise Unicode (NFC first, then diacritic folding as in FR-30 and FR-44) so a decomposed (NFD) STOP cannot slip past a pattern or a length limit; homoglyph (look-alike character) handling is not claimed (G-17). Folding never causes a false opt-out on a diacritic-bearing word (FR-45). Scraped listing text is delimited and clipped in every prompt, including the lead-notes prompt (FR-46). No customer text is logged or stored beyond what is stored today.
- **NFR-6 No real data.** Dictionaries, tests, fixtures, docs and the changelog use invented names and numbers only. Vietnamese sample chats and exports used as fixtures are fabricated or fully anonymised; no real business names, phone numbers or conversations are committed. Any real-looking name found in a file that a slice edits (for example `Asiifdev` in tests and in `apps/api/scripts/eval-style.ts`) is replaced with an invented name in that slice (1.8.6).
- **NFR-7 Backwards compatibility.** Existing English behaviour (UI text, drafts, footer, opt-out line) is byte-for-byte unchanged (the English `OUTPUT_RULES` block is the empty string, FR-21, so the English prompts that exist today do not change), with **exactly these deliberate exemptions**, and no others: (1) FR-26 and FR-25 remove Indonesian-only rules and rewrites that today run on English drafts too (for example the forced "Halo, Kak." greeting in `plain-text.ts`, Indonesian outreach and risk word lists); (2) the **lead-notes prompt** in `ai/marketing-ai.service.ts`, which FR-46 changes for English as well (a security fix; its snapshot is updated deliberately in the same slice, OG-4); (3) the **protocol-marker and speaker-label text** (FR-32) wherever it appears in a prompt, in every language (Indonesian labels become `Me:` / `Them:` / `INTENT:` / `REPLY:` / `NO:`); (4) prompts whose English-request wording changes because their instructions become an English instruction set (FR-21, FR-37): (a) the **brief**, **lead-fit** and **email-subject** prompts, which have an English output today but carry **Indonesian instructions** for English requests, so they cannot stay byte-identical; (b) prompts that have **no English version today** (the reply prompt `buildDraftMessages` in `ai/chat-import/style-prompt.ts`, the reply judge, the intent prompt and the `POST /style/draft` prompt are Indonesian only, FR-21, FR-42, FR-43), whose English wording is new. Both groups are covered by their own tests, not by the snapshot; (5) the **email-subject length cap** (FR-28): the cap changes from 70 to 60 characters (cut by code point to 57 plus `...`), which also changes English subjects of 61 to 70 characters; this is an **accepted deviation** from byte-identical English behaviour. (6) **shipped, review fix MEDIUM-1:** the RULES line of the 11 outreach prompts no longer interpolates the scraped category or name (it points at the data block, so scraped text stays inside `<data_*>`); each has a reasoned `EXEMPT` entry. Of the snapshots, only `describeStyle.english` stays byte-identical to the pre-change snapshot (the design said every outreach prompt would), enforced by the committed snapshot test `apps/api/src/ai/prompt-snapshots.test.ts` with `apps/api/src/ai/__snapshots__/english-prompts.json` (AC-28). No destructive database change (1.7). Stored `"indonesian"` rows, stored Indonesian hint text in sent messages, stored `style_profiles.stats` and stored lost reasons all remain readable.
- **NFR-8 Invariants unchanged.** Nothing sends without approval (drafts only enter the queue through `MessagingService.approve`); claim-then-send; send policy is pure and unchanged; opt-out is absolute and checked at approve and at send; email footer and `List-Unsubscribe` on every email; untrusted inbound text delimited; evidence grounded; `AiClientService.forWorkspace` stays the only reader of `OPENAI_*`. Pacing limits, quiet hours and caps do not depend on the language.
- **NFR-9 Quality bar for Vietnamese.** Dictionaries, canned replies, the opt-out line, the footer and the unsubscribe page are reviewed by a native Vietnamese speaker before merge. AI output quality is judged on a fixed fixture set (AC-9) with a documented rubric (diacritics, register, naturalness, grounding), not by one-off manual impressions.
- **NFR-10 Accessibility.** `<html lang>` matches the displayed language; the toggle keeps keyboard focus styles and `aria-pressed`; English fragments inside Vietnamese pages (unsubscribe page) are marked `lang="en"`.
- **NFR-11 Maintainability.** One language type, one normaliser (both in `apps/api/src/common/language.ts`), one locale helper, one Lang-to-API mapping (both in `apps/web/src/lib/i18n/lang.ts`). Adding a third language later must require changes in these places plus the dictionaries and prompts, not a search for string comparisons, and the compiler finds every table that needs a new entry: each per-language table is a `Record<OutputLanguage, …>` (FR-49), so a third value in `OUTPUT_LANGUAGES` is a compile error until every table is filled in. (The API and the web do not share the type at runtime, FR-16; the web union is updated by hand and AC-6 / AC-7 catch drift.)

### 1.7 Legacy data compatibility for stored `"indonesian"` values

What exists: `campaigns.language` and `marketing_briefs.language` hold `"indonesian"` for every row created with the default, plus `"english"` for the others; `outbound_messages.context.language` (email drafts) and `marketing_briefs.content.campaign.language` (JSON) may hold it too; sent WhatsApp bodies carry the Indonesian opt-out line; `style_profiles.stats` has `language.indonesian`; `leads.lostReason` and `message_opt_outs.reason` may hold "Meminta berhenti (STOP)".

Options considered:

| Option | What it does | Verdict |
|--------|--------------|---------|
| **A. Read-time normalisation to English, no row change (recommended)** | One normaliser at the point of use maps every value other than `"vietnamese"` to `"english"`; the column default changes to `"vietnamese"` for new rows; no data is rewritten. | Chosen. Non-destructive and reversible (rolling back the code restores the old behaviour with the old data), works for JSON copies and queued email drafts that a SQL update would miss, consistent with the UI fallback (cookie `id` reads as English), and never silently writes to a business in a language its owner did not choose. The cost: an old campaign that was set up for Indonesian now drafts in English until the owner switches it to Vietnamese (through the API with `PATCH /campaigns/:id`, or by regenerating the brief; no web screen edits the language, FR-19 c); the UI shows the effective language (FR-15) so this is visible. |
| B. Read-time normalisation to Vietnamese | Same as A but the fallback is `"vietnamese"`. | Rejected as the default: it would start writing Vietnamese to leads that were set up in Indonesian and to any unknown or corrupted value. It can be adopted later by changing one line in the normaliser if the product owner decides every legacy campaign is a Vietnamese-market one (confirm in OQ-3). |
| C. One-off data migration `UPDATE campaigns/marketing_briefs SET language = 'vietnamese' WHERE language = 'indonesian'` | Rewrites rows. | Rejected: destructive (the original choice is lost), flips the outreach language of in-flight campaigns without the owner's action, misses the JSON copies (`content.campaign.language`, `outbound_messages.context`), and cannot be undone from the data alone. |
| D. Keep `"indonesian"` readable as a hidden third language | Keeps the Indonesian prompts and rules. | Rejected: contradicts the decision to replace Indonesian and keeps all the dead code FR-37 removes. |

Migration facts: `packages/database/prisma/migrations/` exists and CI applies it with `db:deploy` (`.github/workflows/ci.yml`), while local development uses `db:push`. The earlier migrations embed `DEFAULT 'indonesian'` (`20260630000000_init`, `20261011020000_marketing_brief`); they are history and must not be edited. A new migration, **hand-written** (not generated from `db:migrate`, to guarantee it contains nothing else), is named `YYYYMMDDHHMMSS_<name>` with a `20261023…` timestamp (the latest existing migration is `20261014010000_message_attachments`, verified; no `20261023…` directory exists yet) and contains only `ALTER TABLE "campaigns" ALTER COLUMN "language" SET DEFAULT 'vietnamese'` and the same for `"marketing_briefs"`. It is verified with `prisma migrate diff` (migrated database against `schema.prisma`) that nothing else differs. No row is rewritten: on PostgreSQL 16 changing a column default is a catalog-only change, so there is no table rewrite, no long lock and no backfill concern.

Other stored legacy items: the Indonesian opt-out hint stays recognised and stripped (FR-29); `style_profiles.stats` without `language.vietnamese` is tolerated (FR-27); old lost-reason text is left (FR-33); stored email footers are not re-rendered (they were rendered at send time).

### 1.8 Explicitly out of scope, and items that need a decision

Out of scope for this feature (market data or infrastructure, not UI language). They keep working as they do today and are not removed:

### 2.1 Feature description

Today Prospex can be used in Vietnamese and writes Vietnamese drafts (section 1), but discovery and sending are still wired to Indonesia: the Google Maps search is suffixed `, Indonesia` and uses `hl=id`, the area expansion knows only Indonesian cities, a local number `0...` becomes `62...`, region lookup returns nothing outside Indonesia, and the campaign form suggests "Jakarta". A Vietnamese business that opens a campaign today gets wrong or empty results and wrongly normalised phone numbers.

This feature adds a **market** concept with two markets, `ID` (Indonesia, the default, behaviour unchanged) and `VN` (Vietnam), each described by a **MarketProfile** (country and calling code, Google Maps language, locale and timezone, area-search suffix, city list and aliases, region dataset, phone rules, default quiet-hours timezone). A campaign for a Vietnamese business, for example a customs-brokerage company in Ho Chi Minh City selling to importers and exporters, then runs end to end: discover leads on Google Maps in Vietnam, normalise Vietnamese phone numbers, work out which numbers can receive WhatsApp, score the leads, filter by Vietnamese region, respect quiet hours in the right timezone, with the market chosen in the campaign form.

Decisions already made (not to be reopened): Vietnam is supported **next to** Indonesia, not instead of it; **Indonesian behaviour must stay unchanged** (2/VM-NFR-1); the markets are `ID` and `VN` only.

Related sections: 1 (Vietnamese language: the output language of a campaign stays independent of its market, see VM-FR-3), 1/OQ-9 and 1.14 (the gap list this section closes). Invariants in `CLAUDE.md` for Messaging (approval, opt-out, send policy is pure), Marketing (the scraper never fabricates leads, no hard-coded city or industry weights, anything opening a user URL goes through `url-fetch.ts`) and multi-tenancy (new per-business state hangs off `workspaceId`) stay unchanged.

### 2.2 User story

As a **Vietnamese business owner** (for example a customs-brokerage company in Ho Chi Minh City), I want to **create a campaign for my market, find importers and exporters on Google Maps in Vietnam and contact the ones reachable on WhatsApp, with correct phone numbers, regions and sending hours** so that **the leads, the numbers and the sending schedule fit Vietnam, without hand-fixing country codes or timezones.**

Secondary: As an **Indonesian user**, I want everything I do today to work exactly as before.

### 2.4 Functional requirements

#### A. Market model and profiles

- **VM-FR-1** A **market** is one of `ID` or `VN` (`type Market`, a shared constant list like `OUTPUT_LANGUAGES` in `common/language.ts`, in a new `common/market.ts`). `MARKETS` is a frozen `['ID','VN']`, `DEFAULT_MARKET = 'ID'`. `normalizeMarket(value: unknown): Market` returns `VN` only for the exact string `VN` and `ID` for everything else, including `null`, missing and unknown values (same defensive rule as `toOutputLanguage`, 1/FR-19); it is used for reads. `toMarket(value: unknown): Market` throws on anything else and is used for writes. Request fields named `market` are validated with a shared `IsMarket()` DTO decorator (`IsIn(MARKETS)`; uppercase only, case-sensitive; `null`, `''` and arrays are 400, `null` through the same `ValidateIf` pattern as `IsOutputLanguage`, 1/FR-17). `common/market.ts` sits beside `language.ts` and must not import from scraper, leads or messaging.
- **VM-FR-2** A **MarketProfile** is a typed, code-level registry (`Record<Market, MarketProfile>`), not a database table (a database table is a rejected alternative: plans and markets would then need seeding and migrations for what is static reference data; see VM-OQ-1 for the one place where state must be stored). `MARKET` is a frozen `Record<Market, MarketProfile>` checked with `satisfies` for exhaustiveness. `MarketProfile` holds: `callingCode` (`'62' | '84'`), `bareMobileLead` (`RegExp | null`: the bare-number rule, `8...` for ID, `null` for VN), `mapsLocale` (`'id-ID' | 'vi-VN'`), `timezone` (`Asia/Jakarta` / `Asia/Ho_Chi_Minh`), `mapCenter` (`{lat, lng}`), `nominatimCountry` (`'id' | 'vn'`), `cities` (`readonly string[]`, ordered), `nationwideTerms` (`readonly string[]`) and `regionSuffix` (country name appended when locating an area: `"Indonesia"` / `"Việt Nam"`; the Maps `hl` value follows from `mapsLocale`). Place aliases, separator words and the province dataset live in `scraper/areas.ts` and `leads/geo.ts` next to the code that uses them, not in the profile (this keeps `common/market.ts` free of scraper and leads imports). Phone rules are the pure functions of VM-FR-9 to VM-FR-12 in `messaging/phone.ts`, and `phoneKind` is in `common/market.ts`.
- **VM-FR-3** The market and the output language are **independent**: a `VN` campaign may be written in `english`, an `ID` campaign in `vietnamese` (the language rules of section 1 are not touched). The form may preselect the language from the market but never forces it.
- **VM-FR-4** The `ID` profile reproduces today's behaviour exactly: `, Indonesia`, `hl=id`, `id-ID`, `Asia/Jakarta`, `INDONESIA_CITIES` (same 70 names in the same order), `PLACE_ALIASES`, the `NATIONWIDE` pattern, `splitAreas` words and prefixes, `accept-language=id`, calling code `62` with the `8...` rule. Existing exports keep their current signatures and results: `normalizePhone(raw, defaultCountryCode = '62')`, `phoneFromJid`, `phoneFromKey`, `INDONESIA_CITIES`, `isNationwide(location, market = 'ID')`, `planAreas(location, q, max, market = 'ID')`, `splitAreas`, `stripPlaces`, `haversineKm`, `DEFAULT_RADIUS_KM`, `inArea`, `normalizeProvince`, `regionFromNominatim`, `cellKey`, `normalizeRating(raw, market = 'ID')`, `pickCategory`. New parameters are optional and trailing with default `ID`; new phone entry point `normalizePhoneFor(raw, market)` (for `ID` exactly `normalizePhone(raw, '62')`). A committed **regression snapshot** is a set of table-driven `*.snapshot.test.ts` files with **inline literals** (not generated files): about 60 `ID` phone inputs including a hostile 10 kB one, and the outputs of areas, geo, maps-parse, the dedupe key and wa-text, committed **before** any behaviour change (2/VM-AC-1, 2/VM-NFR-1).
- **VM-FR-5** **Where the market lives (decided, VM-OQ-1): one `market` column per campaign** (`campaigns.market`, `TEXT NOT NULL DEFAULT 'ID'`), because the scraper, the phone normaliser for scraped leads and the area expansion already run with a campaign, and a single login can own both an Indonesian and a Vietnamese campaign. A lead's market is always `lead.campaign.market`: `Lead.campaignId` is required and referral leads copy it, so there are no orphan leads and no `lead.market` column. Inbound needs no market (Baileys numbers arrive international and match `phoneE164`). Quiet-hours timezone stays **per workspace** on the WhatsApp and email accounts (VM-FR-16), because sending limits belong to the sending number.

#### B. Discovery (Google Maps)

- **VM-FR-6** The scraper takes the market of the campaign (`ScraperJobData.market`, default `ID` when the queued job lacks it, so jobs already in Redis keep working) and builds all Maps URLs and the browser context from the profile: `<area>, <areaSuffix>` and `?hl=<hl>` in both URLs, `locale` and `timezoneId` in `newContext`. For `VN`: `, Việt Nam`, `hl=vi`, `locale` `vi-VN`, `timezoneId` `Asia/Ho_Chi_Minh`; for `ID`: `, Indonesia`, `hl=id`, `id-ID`, `Asia/Jakarta` (all from the profile). The job payload carries the market but the processor **reads the market from the database at job start** (the payload is only the fallback; missing means `ID`), which closes the race between `PATCH` and start (VM-FR-24). The market reaches `page.evaluate` only as a value from the closed enum, and the URL is built with `encodeURIComponent(query + ' ' + area)`.
- **VM-FR-7** **Vietnamese area expansion.** For `VN` the area logic uses the `VN` profile. (a) A nationwide search (`toàn quốc`, `cả nước`, `Việt Nam`, `Viet Nam`, `Vietnam`, `nationwide`, `all Vietnam`) expands to the top cities of the VN list, same sizing rules as today (at least 8, at most the list length, `perSearch` formula unchanged). (b) A place the user typed (ward, district, street area, any name not in the lists) stays **as typed**; only the market's prefixes (`thành phố`, `tp.`, `tỉnh`, `tại`, `ở`) are stripped and the market's separator words (`và`, `hoặc`, `cùng với`, plus the common ones: `,` `;` newline `|` `/` `+` ` & `) split. (c) **Aliases resolve with and without diacritics, case-insensitively, with `đ` folded to `d`**: `Ho Chi Minh`, `Ho Chi Minh City`, `HCM`, `HCMC`, `TP.HCM`, `TPHCM`, `TP. HCM`, `Sài Gòn`, `Sai Gon`, `Saigon`, `TP. Hồ Chí Minh`, `Thành phố Hồ Chí Minh` all resolve to one canonical place; the same for Hà Nội (`Ha Noi`, `Hanoi`, `HN`), Đà Nẵng (`Da Nang`, `Danang`) and every other city in the list. A canonical place that is also contained in a search phrase is removed from the phrase by `stripPlaces`, as for Indonesia. (c2) **A comma separates places in both markets** (current `splitAreas`, no heuristic): `Quận 7, TP.HCM` is two searches; the help text says so. (d) Matching never uses a regex built from unescaped input and stays linear (VM-NFR-3).
- **VM-FR-8** **Vietnamese Maps parsing when `hl=vi`.** The pure helpers in `scraper/maps-parse.ts` (and the browser-side extraction that today duplicates their rules) gain market-aware rules, all additive and covered by fixtures of **invented** HTML: (a) rating `4,6` and `4.6` (already handled; keep) and the aria-label wording `4,6 sao`; (b) review counts `(1.234)`, `(1,234)`, `1.234 bài đánh giá` read as 1234 (dot is a thousands separator in Vietnamese, comma a decimal one; a bare `(4,6)` is a rating, not a count); (c) the labels `Địa chỉ`, `Điện thoại`, `Trang web` and the words for opening hours and state (`Mở cửa`, `Đóng cửa`, `Mở cửa cả ngày`, `Đóng cửa vĩnh viễn`, `Tạm thời đóng cửa`, `Mở cửa lúc`, `Đóng cửa lúc`, `Đang mở cửa`, `Quảng cáo`) are known so that `pickCategory` never returns them as a category and an opening-hours row is not read as an address; (d) address rows are recognised by Vietnamese street words (`Đường`, `Phố`, `Số`, `Phường`, `Xã`, `Quận`, `Huyện`, `KCN`, `Ngõ`, `Hẻm`, `Tổ`) in addition to the Indonesian ones; (e) phone text is accepted when it looks like a Vietnamese number in any of the shapes of VM-FR-9 (including a leading `(`), not only `+62`, `08` and `^\d{3}[\s-]\d`; (f) the end-of-list text, `Hasil`/`Results` selectors and the search-box selector accept the Vietnamese equivalents (`Bạn đã xem hết danh sách`, `Kết quả`, `Tìm kiếm trên Google Maps`; exact strings to be confirmed on a real run, see 2.10). The `ID` rules stay in force for `ID` (no Vietnamese word may change an Indonesian parse; `Mở`/`Đóng` rows are unreachable for `ID`).

#### C. Phone numbers

- **VM-FR-9** Vietnamese normalisation (`VN` profile; `normalizePhone` keeps its signature and gains an optional market or a profile argument, the default stays `62`): input may contain spaces, dots, dashes, parentheses and a `+`. `+84 90 123 4567`, `84901234567`, `0901234567`, `090 123 4567`, `090.123.4567`, `090-123-4567`, `0084 901234567` all give `84901234567`. A landline such as `(028) 3822 1234`, `028 3822 1234`, `+84 28 3822 1234` gives `842838221234`. The optional trunk zero after the code (`+84 (0) 90...`, `+84 090...`) is dropped. Output is digits only, as today. Valid national significant number: 9 digits (mobile) or 9 to 10 digits (landline; the exact length rules are verified by QA against the national numbering plan, see 2.10); anything else returns `null`.
- **VM-FR-10** **WhatsApp-capable classification.** A pure function `phoneKind(e164, market)` returns `mobile`, `landline`, `service` or `unknown`. For `VN`: national number starting `03`, `05`, `07`, `08`, `09` (after the trunk zero) is `mobile` and treated as **WhatsApp-capable** (a heuristic, not proof); `02x` is `landline` and **not** WhatsApp-capable; `1800` and `1900` (service numbers) are `service`, **only for raw-input classification** (the manual-number form says "service number, not WhatsApp-capable"); `normalizePhone` still returns `null` for them, so a stored lead never carries `service`. `phoneKind` is computed from `phoneE164` and the lead's campaign market (no column; VM-OQ-6). For `ID` the function returns `unknown` for every number and the existing behaviour (no filtering) is kept. `unknown` (international numbers, all `ID` numbers) is selectable, not penalised, and scored as `ID` is today. Server-side enforcement is in VM-FR-25. A landline lead is still stored (name, address, other channels), but is not offered for WhatsApp bulk selection and is reported as "landline: cannot be reached on WhatsApp" wherever `reachable` is computed (`template.service.ts`, the Outbox lead list). The real check stays `onWhatsApp()` at send time (`BaileysProvider.resolve`); this requirement adds no pre-send network call.
- **VM-FR-11** International numbers are kept: a `+` number with another country code (`+65...`, `+1...`) is not rewritten by either market; it is classified `unknown` and follows the existing length rule (8 to 15 digits). Indonesian numbers in a `VN` campaign (`+62 812...`) are kept as `62...`.
- **VM-FR-12** The market of the **lead's campaign** decides the default calling code when a lead is saved from a scrape (`leads.service.ts:209`, the dedupe key at `scraper.processor.ts:18`, the scraper's browser-side phone clean-up at `google-maps.scraper.ts:232`). **The page returns raw digits and the phone is normalised in Node** (this removes the in-page `replace(/^62/,"0")`; if a slice cannot do that, the only alternative is passing a trunk calling code from a closed set as a `page.evaluate` argument). `createMany(leads, market = 'ID')` takes the market, including the one call in `scraper.processor.ts`. For every phone belonging to a **lead**, the lead's campaign market wins over the account code: `normalizePhone(x, account.defaultCountryCode)` at `messaging.service.ts:~198`, `template.service.ts:~58` and `:~101`, and `leads.service.ts:~133` (referrals copy the campaign) use the campaign market's calling code. `WhatsappAccount.defaultCountryCode` stays (not dropped, so `ID` is unchanged) **only for free-typed numbers with no lead** (`messaging.service.ts:~243`, `:~315`). The legacy backfill (`inbound.service.ts:~60`) selects `campaign.market` and uses that market's calling code. `wa-text.ts:~90` gets a bounded Vietnamese alternative `(\+?84|0)(3|5|7|8|9)\d{8}` (its input is already sliced to 4000 characters). **Phone input longer than 64 characters is rejected**: the API DTO has `MaxLength(64)` (400) and `normalizePhone` returns `null` for `raw.length > 64`, checked before any regex, in both markets; the `ID` snapshot must prove no `ID` result changes, and if any `ID` snapshot differs the cap is gated to the `VN` path. Hostile input (very long digit strings, nested parentheses, 100,000-character strings; a 10 MB test via `common/hostile-limits.ts`) is processed in linear time (VM-NFR-3).

#### D. Region data

- **VM-FR-13** `regionFromNominatim` keeps its signature and dispatches **by the `country_code` in the answer, not by campaign**. For `id` the code path and results stay as they are. For `vn` it branches to a new `regionFromNominatimVN` and returns `{ province, regency, district }` where `province` is the province-level unit (tỉnh or thành phố trực thuộc trung ương) normalised to the **current official name without the prefix** (`Thành phố Hồ Chí Minh` becomes `Hồ Chí Minh`, `Tỉnh Đồng Nai` becomes `Đồng Nai`); `regency` and `district` follow VM-OQ-3. The geocoder is asked with `accept-language=vi` for `VN` (VM-FR-2). A small bundled dataset of province names (a TypeScript list, no database table) is used to normalise spellings and, for the region filter, to list provinces even before any lead has one.
- **VM-FR-14** **Dataset and date.** Vietnam reorganised its provinces in 2025: by the National Assembly resolution on arrangement of province-level units effective **1 July 2025**, the 63 province-level units became **34** (28 provinces and 6 centrally-run cities: Hà Nội, Thành phố Hồ Chí Minh, Hải Phòng, Đà Nẵng, Cần Thơ, Huế), and the district level was abolished (two-tier local government: province and commune/ward). Ho Chi Minh City now includes the former Bình Dương and Bà Rịa-Vũng Tàu. **This is stated from the writer's recollection and has not been verified against an official source** (no web access in this drafting step): the implementation slice that adds the dataset must cite the official resolution and list (and date its access) in the dataset's header comment and in `docs/features.md`, and must not ship the list before that check. Until then, older OSM or Maps data may still return the pre-merger names (for example a district in the former Bình Dương); the normaliser maps a known pre-merger province name to its current unit only for names covered by the verified mapping, and otherwise keeps the name as returned. The 34-province post-July-2025 list is used for the **area planner only**; geo takes what OSM returns. Keep the dataset small: province names, aliases and (optionally) the pre-merger-to-current mapping; no ward list, no invented entries.
- **VM-FR-15** The leads region filter (province, regency, district, `region-filter.tsx`, `GET /leads` filters) lists the regions that exist in the current lead set as today, and works for Vietnamese leads without code change in the endpoints; API labels of the three levels are unchanged (VM-OQ-3 decided: no relabelling, no schema change). - **VM-FR-22** Google Maps is **never** scraped in automated tests. Fixtures are invented HTML or JSON snippets (example.com, "Công ty Ví Dụ"; invented phone numbers in documentation ranges are not available for Vietnam, so numbers are visibly fake, such as `0900 000 001`). `SCRAPER_MODE=fixture` produces labelled leads per market: `[Test data]` names, source `fixture`, no phone and no website as today, with the area text and a market-appropriate city for a nationwide search; they can never be contacted. Fixture leads carry the market's fixed fixture region and coordinates (`VN`: Hồ Chí Minh, 10.7769, 106.7009; `ID`: the current output, unchanged), so a province filter works with `GEOCODER_DISABLED=true`. Fabrication exists only under `SCRAPER_MODE=fixture`.
- **VM-FR-23** One additive Prisma migration `packages/database/prisma/migrations/20261024000000_campaign_market/migration.sql` adds `campaigns.market TEXT NOT NULL DEFAULT 'ID'` (PostgreSQL 11 or later: metadata-only, no table rewrite; no index, no CHECK, as for `language`; validation is in the DTO and `toMarket`; `schema.prisma` gets `market String @default("ID")`; `Unsupported("vector")` columns untouched; run `prisma generate` after). Existing rows get `'ID'` and behave as before. The migration folder contains the commented **reverse SQL** (`-- reverse: ALTER TABLE "campaigns" DROP COLUMN "market";`), is verified on a scratch database (deploy chain, `prisma migrate diff` exit 0, negative control) as in 1.14, and the shared development database is not changed by the slice.
- **VM-FR-24** *(Draft-only market, enforced in SQL; added by the architect.)* `PATCH /campaigns/:id` changes the market only when `dto.market` is present, with `updateMany({ where: { id, workspaceId, status: 'draft' }, data: { market } })`. A campaign not found in the caller's workspace is 404 (checked first). The scraper worker reads the market from the database at job start (VM-FR-6). To change the market of a started campaign the owner creates a new campaign (cloning is out of scope).
- **VM-FR-25** *(Landline guard, server side; added by the architect.)* Logic lives in pure `common/market.ts` (`phoneKind`); `send-policy.ts` stays about pacing. (a) `MessagingService.approve` rejects a WhatsApp-channel message to a lead whose `phoneKind` is `landline` or `service` with 400 `Not a mobile number`; the draft stays `draft`. (b) `SenderService.deliver`, before the provider call, applies the same check: the message becomes `failed` with error `Not a mobile number` and is never sent. `unknown` is allowed. Opt-out ordering is unchanged, and no phone number is written to logs.

### 2.5 Non-functional requirements

- **VM-NFR-1** **Indonesian regression.** For `ID` (the default, and every row and queued job without a market) behaviour is byte-identical: same URLs, same locale, same city order, same phone output, same region output, same scores. Proven by the regression snapshot (2/VM-AC-1) and the existing 732 API unit tests passing unchanged (the figure from 1.14; re-measured at the start of the slice). The snapshot tests are committed **first** (slice S1, no production change) and **may not be edited later in this feature**: a diff in them is a BLOCKER in review.
- **VM-NFR-2** **Security.** `market` is validated by an allow-list; a stored or queued unknown value reads as `ID` and is never interpolated into a URL, a prompt or SQL. The Maps URLs are built from profile constants plus the already-sanitised query. Nothing that opens a user-supplied address changes (`url-fetch.ts`). The new `market` field is workspace-scoped through its campaign and returned only inside the campaign's own routes.
- **VM-NFR-3** **Linear, bounded parsing.** Phone, area, alias and Maps-text parsing for `VN` stays linear: inputs are capped before matching (phone text 64 characters, rejected above it per VM-FR-12; area text 400), aliases are matched as escaped literals after Unicode normalisation (NFC then diacritic folding), no regex backtracks on unclosed brackets. Hostile-input tests with time limits are added to the existing suites (strings of 100,000 characters, repeated `(`, repeated spaces and dots, mixed scripts). The accent folding helper is shared with `common/text.ts` (1/FR-44), not duplicated.
- **VM-NFR-4** **Performance.** No added network call per lead; the geocoder rate limit (1 request per 1.1 s) and the cell cache are unchanged; area expansion and phone parsing add no measurable time to a 1,500-lead campaign.
- **VM-NFR-5** **Compatibility.** Queued BullMQ jobs and existing rows without `market` keep working (VM-FR-6). The API contract only gains an optional field; no existing request fails.
- **VM-NFR-6** **Honesty about verification.** Every claim about Google Maps behaviour in Vietnamese is labelled **Simulated** until a real run is done (2.10); nothing in the docs says Vietnamese discovery is verified.

### 2.10 Open questions, design questions and unverified items

Design questions for the **architect** (the PRD gave a recommendation, the architect decided; **VM-OQ-1 to VM-OQ-6 are all resolved in 2.13**, and where the option text below differs from 2.13, 2.13 wins):

- **VM-OQ-1 Where does the market live?** Options: (A) **per campaign**, `campaigns.market` (recommended, VM-FR-5: it matches how the scraper and leads are already scoped, allows one workspace to run both markets, one additive column); (B) **per workspace** (one default for everything; simple for the form and the sending account, but a workspace can then never serve both markets, and existing workspaces need a backfill rule); (C) **derived from the location text** (no schema change, but `Hanoi` versus a Vietnamese-named street in Indonesia and typos make it unreliable, and the user cannot override it; not recommended). A hybrid is possible: campaign column plus a workspace default used only to preselect the form.
- **VM-OQ-2 Timezone default for new accounts.** Set at creation from the first campaign's market (VM-FR-16), or leave the model default and only change the panel's initial value? Because Jakarta and Ho Chi Minh share UTC+7 the result is the same in hours; the recommendation is the lighter option (panel and fallback only, no migration of `whatsapp_accounts`/`email_accounts` defaults) unless the architect wants the stored value to read correctly.
- **VM-OQ-3 How do the three region columns map to Vietnam after the 2025 reform?** Recommendation: `province` = province-level unit, `regency` = former district (`quận`/`huyện`) when the geocoder still returns it, left empty otherwise, `district` = ward or commune (`phường`/`xã`). Alternative: add a market-aware label layer and leave `regency` always empty for `VN`. Needs a check of what Nominatim actually returns for Vietnamese addresses today (not verified).
- **VM-OQ-4 Comma versus ward.** `splitAreas` treats a comma as a separator, so `Quận 7, TP.HCM` becomes two searches (`Quận 7` and `TP.HCM`), each searched alone. Recommendation: keep the rule (no heuristics), tell users in the help text to write `Quận 7 TP.HCM` for one place, and cover it with a test; alternative: for `VN`, join a leading ward/district word with the following city.
- **VM-OQ-5 Can the market of a started campaign change?** Recommendation: only while `draft` (leads, phone numbers and regions already depend on it).
- **VM-OQ-6 Is `phoneKind` computed or stored?** Recommendation: computed from `phoneE164` and the campaign market (no column), so no backfill; the architect may prefer a stored `Lead.waCapable` if filtering at scale needs an index.

Questions for the **user** (not product decisions of this PRD, flagged for the owner):

- **VM-OQ-7 Compliance.** Sending unsolicited commercial messages in Vietnam is regulated; the writer recalls that Decree 91/2020/ND-CP on anti-spam messages, calls and emails sets rules on unsolicited messages (consent, opt-out, a registered sender for some channels). This is **not legal advice and was not verified**. It is a risk for the owner to review with a qualified adviser before using the WhatsApp channel in Vietnam. Product behaviour that already helps (approval before send, absolute opt-out, pacing) is unchanged, and the PRD adds no compliance claim; VM-FR-26 adds a static risk notice, not a claim.
- **VM-OQ-8 City list for nationwide search.** The ordered list of Vietnamese cities (about 30 real names, biggest markets first) needs the owner's review: after the 2025 mergers some well-known cities (for example Vũng Tàu, Thủ Dầu Một, Biên Hòa) now belong to other province-level units; they stay valid as **search terms**, since people and Google Maps still use them.
- **VM-OQ-9 Default market in the form** for a user whose interface is Vietnamese: resolved, `VN` (the UI-language rule of VM-FR-18).

**Out of scope:** the official WhatsApp Cloud API (hosted-only, separate private package); a **Zalo** channel (a likely future channel for Vietnam, not part of this feature; the design does not block it: the market profile and `phoneKind` are channel-neutral); markets other than `ID` and `VN`; currency and price formatting (`Rp`, VND; 1/OQ-6 stays open); a database-backed profile table or an admin screen to edit profiles; a pre-send WhatsApp-capability network check; verification by a **real** Google Maps run (see below); ward-level datasets; English or Indonesian translation changes; Vietnamese contact-page keywords (`liên hệ`, `giới thiệu`) in website enrichment (follow-up; `contact-extract.ts` only takes `+international` numbers and is already market-neutral); cloning or re-running a campaign into another market (create a new campaign); the same number in an `ID` and a `VN` campaign (dedupe stays per workspace on `phoneE164`, the first lead wins; documented).
